# Manual New-Problem Session Reset Design

## Goal

Let the tracker owner decide when a new practice session begins while continuing to count genuinely
new Problems automatically and preserving all Notion history.

## User experience

The dashboard summary is labeled `NEW PROBLEMS THIS SESSION` and continues to display
`current / maximum`. The existing Dashboard Settings dialog retains the configurable maximum and
adds a `Reset current count` action.

Selecting reset opens a confirmation prompt that asks whether to reset the new-problems count to
zero. Cancelling changes nothing. Confirming persists the current timestamp as the session boundary
and immediately renders `0 / maximum`. Each Problem whose immutable `First Attempt` timestamp is
later than that boundary increases the current count automatically.

The maximum remains an integer from 1 through 100. Resetting the current count does not change the
maximum.

## Persistence and data flow

The ignored local dashboard settings file stores both `dailyNewProblemGoal` and an optional
`newProblemSessionStartedAt` ISO timestamp. Existing settings files without the timestamp remain
valid and preserve the current calendar-day count until the first manual reset.

The bridge's narrow `POST /dashboard/settings` API accepts exactly one of two request shapes:

- `{ "dailyNewProblemGoal": number }` updates the maximum; or
- `{ "resetNewProblemSession": true }` resets the session boundary to the bridge's current time.

After a reset is durably written, the in-memory dashboard uses the new boundary and the response
returns the updated count and maximum needed for immediate rendering. A later refresh or bridge
restart loads the same boundary and queries Notion for Problems whose `First Attempt` is strictly
after it.

The reset timestamp is generated by the bridge rather than accepted from the browser. The existing
per-process anti-forgery token remains required, and the route stays same-origin with no CORS.

## Safety boundaries

Reset is presentation configuration only. It must not write to Notion or modify Problems, Attempts,
Practice State, Solved Streak, First Attempt, Last Attempt, Next Review, captured code, External Key,
or Client Event ID. It does not alter the review queue or review schedule.

The settings file must be written atomically before the in-memory boundary changes. If persistence
fails, the displayed count and stored boundary remain unchanged and the dialog shows an actionable
error. Rapid settings operations remain serialized so the last accepted operation wins.

## Verification

Focused tests will establish the behavior before implementation and cover:

- backward-compatible loading of settings without a session boundary;
- strict parsing and atomic persistence of the boundary;
- authenticated reset requests and rejection of browser-supplied timestamps or extra fields;
- unchanged state when persistence fails;
- counting `First Attempt` values after the boundary while preserving the legacy daily query before
  the first reset;
- confirmation and cancellation behavior;
- immediate `0 / maximum` rendering after reset;
- automatic increments after a subsequent first-time Problem;
- persistence across dashboard refresh and bridge restart; and
- the unchanged review, capture, Notion schema, and idempotency contracts.

Tests created or changed by this effort are development evidence rather than independent
verification. Completion also requires the repository's existing `npm run check`, version
consistency, `git diff --check`, and live desktop/mobile dashboard inspection.

## Release and documentation

This is a shipped code change and therefore increments the synchronized patch version from `0.1.6`
to `0.1.7`. README, STATUS, architecture, and the current milestone handoff will describe the
session-based counter and its local-only reset boundary. No new milestone is needed for this focused
follow-up.
